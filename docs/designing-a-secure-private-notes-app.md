# 设计一个安全私密的笔记应用

笔记应用往往承载着使用者最不设防的内容：未完成的想法、情绪记录、密码草稿、身体或心理健康细节、人际关系中的矛盾。这类内容一旦泄露，伤害通常不是"数据被看到"这么简单，而是关系、职业乃至安全层面的连锁反应。因此，"安全私密"不应该是笔记应用的一个可选功能，而应该是从第一行代码开始的设计前提。本文尝试从威胁模型、数据存储、访问控制、传输与同步、界面呈现、可核查性六个维度，给出一套可落地的设计思路，并结合本仓库中 Three Column Method 这款 CBT 笔记应用的实际做法作为例子。

## 一、先想清楚"防谁"：威胁模型

在动手写代码之前，先回答一个问题："我们要保护用户，不被谁看到这些内容？"不同答案会导向完全不同的架构：

- **防陌生人捡到/偷走设备**：需要设备锁屏 + 应用锁（生物识别或密码）、防止内容出现在最近任务列表缩略图里、禁止截屏。
- **防身边人"顺手看一眼"**：需要应用切到后台时立刻隐藏内容、通知栏不显示正文摘要、支持给单条记录设置更高强度的二次锁定。
- **防云端服务商或运营者读取数据**：需要端到端加密，密钥只保存在用户设备上，服务商即使能访问数据库也只能看到密文。
- **防网络中间人**：需要传输层加密（TLS）、证书校验，同步协议本身也要做认证与完整性校验。
- **防应用自身被逆向或被恶意二次打包后窃取数据**：需要代码混淆、密钥不硬编码、必要时做完整性校验（Play Integrity / DeviceCheck 之类）。

把这些威胁列成一张表，每一项标注"是否在本产品的范围内"，能避免两个常见错误：一是过度设计（比如给一个纯本地、从不联网的应用做端到端加密的密钥交换协议，纯属浪费）；二是遗漏关键项（比如做了传输加密，却忘了本地锁屏)。以本仓库的应用为例，它是**完全离线**的：没有账号、没有服务端、数据只存在设备本地，用户主动导出/导入才会产生一个文件。这个定位直接简化了威胁模型——不需要考虑服务商信任、不需要考虑网络攻击面，核心风险收敛为"这台设备的物理/系统访问权限落到了不该拥有它的人手里"。

## 二、本地存储：默认加密，而不是"可选开启"

多数笔记应用的数据最终都落在本地数据库（SQLite/Room、Core Data、IndexedDB 等）里。默认情况下这些文件是明文的，任何拿到 root/越狱权限，或者从备份文件中提取数据的人都能直接读出全部内容。几个基本原则：

1. **静态加密（at-rest encryption）作为默认行为**，而不是设置里一个需要用户自己找到并打开的开关。Android 上可以用 SQLCipher 或 Jetpack Security 的 `EncryptedFile`/`EncryptedSharedPreferences`；iOS 得益于系统级的 Data Protection，只要正确设置文件保护级别（`NSFileProtectionComplete`），未解锁状态下文件本身就不可读。
2. **加密密钥不要和数据放在一起**。密钥应存放在系统提供的安全区域——Android 的 Keystore（可选绑定 StrongBox/TEE）、iOS 的 Keychain（结合 Secure Enclave）——而不是写死在代码里或存在明文配置文件中。
3. **关闭系统级自动云备份**，除非你能确保备份链路本身也是加密的、且密钥不会被一并备份走。Android 上这对应 `AndroidManifest.xml` 里的 `android:allowBackup="false"`；否则用户手机被 Google/iCloud 账号接管后，笔记可能连本体一起被同步走。
4. **导出文件同样要认真对待**。很多应用做好了数据库加密，却在"导出为 JSON/CSV"这一步整体放弃了保护——导出文件默认明文写入下载目录，谁都能打开。至少应该：默认导出到应用私有目录而不是公共下载目录，导出前提示用户其中包含敏感信息，有条件的话给导出文件加一个用户自己设的密码。

## 三、访问控制：本地锁 + 分级敏感度

"安全存储"解决的是数据在磁盘上的问题，"访问控制"解决的是数据在屏幕上的问题——也就是有人已经拿到了解锁的设备。

- **应用锁**：用系统的生物识别 API（Android `BiometricPrompt`、iOS `LocalAuthentication`）而不是自己实现指纹/密码比对逻辑，理由很简单——密码学正确性、防暴力破解、防降级攻击这些坑，系统 API 已经踩过了。锁定态下要做到：应用切到后台的瞬间就锁定，而不是等一个超时窗口；从最近任务列表切换回来时先出示锁屏，再渲染内容，避免内容"先闪一下"。
- **防截屏/防录屏与最近任务缩略图脱敏**：Android 的 `FLAG_SECURE` 一行代码可以同时解决"最近任务列表里能看到明文缩略图"和"被截屏/录屏"两个问题，非常高性价比，几乎没有理由不加。iOS 没有对等的系统开关，通常做法是监听 `applicationDidEnterBackground`，切到后台前用一张遮罩视图覆盖内容。
- **敏感通知**：如果应用有推送/提醒功能（比如"该写日记了"），通知内容本身不要包含笔记正文片段，标题用中性文案。
- **分级锁定是进阶但值得考虑的设计**：不是所有内容都需要同一强度的保护。允许用户对"整个应用"设默认锁，同时允许给某几条特别敏感的记录设置"打开这一条需要再验证一次"，这样常用内容访问顺畅，真正敏感的内容有额外一道门。

本仓库的应用目前实现了前两条（可选的生物识别应用锁、隐藏最近任务缩略图/禁止截屏、关闭自动云备份），这是"轻量但覆盖了最常见泄露场景"的一个务实平衡点——没有为了"看起来更安全"去堆砌用户几乎不会用到的高级功能。

## 四、如果涉及同步/多端：端到端加密是唯一诚实的答案

一旦产品要做多设备同步或云备份，"安全私密"的复杂度会跳升一个量级。常见的三种做法，安全性依次递增：

1. **服务端明文存储**：最省事，但意味着服务商（以及任何入侵服务端的人）能读到全部内容。除非产品定位本就不承诺隐私，否则不建议。
2. **服务端静态加密（encryption at rest），密钥由服务端持有**：能防住"数据库被拖库"，但防不住服务商本身，也防不住服务商被合法要求交出数据/密钥。
3. **端到端加密（E2EE）**：加密和解密只发生在用户设备上，密钥从不以明文形式离开设备，服务端只存储密文，即使被攻破也无法读出内容。这是对"私密笔记"最诚实的承诺。

做 E2EE 时几个容易踩的坑：

- **密钥派生要用用户可控的秘密**（主密码、设备密钥对），并用成熟的密钥派生函数（Argon2id、PBKDF2 加足够迭代次数），不要自己发明算法。
- **"忘记密码就找回不了数据"是 E2EE 的必然代价，不是 bug**。如果产品同时宣传"E2EE"又提供"忘记密码一键找回全部笔记"，这两者是矛盾的——要么密钥托管在服务端（不是真正的 E2EE），要么找回的只是账号而不是历史数据。把这个权衡诚实地告诉用户，比暗中留一个后门更负责任。
- **多设备场景下的密钥同步**本身也要加密传输（比如用户在新设备上输入主密码，通过安全通道从旧设备或服务端取回被加密保护的主密钥），避免"每台新设备都重新生成密钥导致历史数据读不出来"这种体验灾难。

## 五、界面设计也是安全设计的一部分

安全不只是后端和存储层的事，界面呈现方式同样会造成信息泄露：

- **视觉上不要"暗示"内容的敏感性**。花哨的图标、鲜艳的强调色、封面缩略图预览文字，都会让人在别人瞥一眼屏幕时立刻意识到"这是一个私密记录类应用"。低调、克制、不使用能让人联想到"日记/心事"的装饰性设计，本身就是一种隐私保护——它降低了"被路过的人一眼认出这是什么"的概率。这也是为什么很多面向敏感场景的应用会刻意选择偏中性、偏"工具感"的视觉语言，而不是温馨可爱或强烈情绪化的设计。
- **锁屏文案不剧透**。锁屏提示语应该只说"解锁查看内容"，不要写出应用具体记录的是什么主题。
- **应用图标与应用名**在锁屏和桌面上也是可被他人看到的信息面，如果场景要求更高的伪装性，可以考虑允许用户自定义显示名称/图标（这属于更进阶的"伪装"需求，需要单独评估是否是产品要支持的场景）。
- **深色/浅色两套主题都要经过同样的隐私考量**，而不是只优化一套然后简单套一层反色——同一套克制的配色逻辑（而不是鲜艳的强调色）在两种模式下都要成立。

## 六、可核查性：把"我们说的"变成"用户能验证的"

最后一层，也是最容易被忽视的一层：安全声明需要是可核查的，而不是营销话术。

- **开源，或至少公开关键的安全实现细节**（用了哪种加密算法、密钥怎么存、有没有做静态加密），让愿意验证的用户或第三方能够核实。
- **完全离线的应用，"不联网"本身就是最强的隐私承诺之一**——建议显式声明"没有账号、没有服务端、除非你主动导出，否则数据不会离开这台设备"，并且工程实现上真的做到零网络请求（比如构建时不引入任何网络库、CI 里可以加一个静态检查确认没有意外的网络调用被引入）。
- **权限最小化**。App 请求的系统权限（相机、麦克风、位置、通讯录……）应该严格对应功能需要，一个笔记应用如果申请了位置权限却没有任何用到定位的功能，会直接削弱"我们重视隐私"这句话的可信度。
- **对外部依赖保持警惕**：第三方 SDK（崩溃上报、统计分析、广告）往往是数据泄露最隐蔽的来源，即使应用自身逻辑无懈可击，一个会上传用户行为数据的 SDK 也会让全部努力归零。私密类应用应该优先做到零第三方数据收集 SDK，或者至少清楚罗列每一个 SDK 收集了什么、发到哪里。

## 小结

安全私密的笔记应用不是靠某一个"加密"功能实现的，而是一整条链路上多层防护叠加的结果：明确威胁模型 → 本地静态加密默认开启 → 应用锁与截屏防护 → 如果涉及同步则做真正的端到端加密而非营销话术 → 界面设计本身不泄露信息 → 用可核查的方式兑现每一句安全承诺。对大多数个人笔记场景而言，"完全离线 + 本地加密 + 应用锁 + 低调不张扬的界面"已经能覆盖绝大部分真实威胁，且实现成本可控；只有在明确需要多设备同步时，才值得投入端到端加密这类更复杂的基础设施。把复杂度花在真正对应威胁模型的地方，而不是堆砌"看起来安全"的功能列表，是这类产品设计中最重要的判断力。
