# 设计一个安全私密的笔记应用

笔记应用往往承载着使用者最不设防的内容：未完成的想法、情绪记录、密码草稿、身体或心理健康细节、人际关系中的矛盾。这类内容一旦泄露，伤害通常不是"数据被看到"这么简单，而是关系、职业乃至安全层面的连锁反应。因此，"安全私密"不应该是笔记应用的一个可选功能，而应该是从第一行代码开始的设计前提。本文尝试从威胁模型、数据存储、访问控制、传输与同步、界面呈现、可核查性六个维度，给出一套可落地的设计思路，并结合本仓库中 Three Column Method 这款 CBT 笔记应用的实际做法作为例子。

## 一、先想清楚"防谁"：威胁模型

在动手写代码之前，先回答一个问题："我们要保护用户，不被谁看到这些内容？"不同答案会导向完全不同的架构：

- **防陌生人捡到/偷走设备**：需要设备锁屏 + 应用锁（生物识别或密码）、防止内容出现在最近任务列表缩略图里、禁止截屏。
- **防身边人"顺手看一眼"**：需要应用切到后台时立刻隐藏内容、通知栏不显示正文摘要、支持给单条记录设置更高强度的二次锁定。
- **防云端服务商或运营者读取数据**：需要端到端加密，密钥只保存在用户设备上，服务商即使能访问数据库也只能看到密文。
- **防网络中间人**：需要传输层加密（TLS）、证书校验，同步协议本身也要做认证与完整性校验。
- **防应用自身被逆向或被恶意二次打包后窃取数据**：需要代码混淆、密钥不硬编码、必要时做完整性校验（Play Integrity / DeviceCheck 之类）。

把这些威胁列成一张表，每一项标注"是否在本产品的范围内"，能避免两个常见错误：一是过度设计（比如给一个纯本地、从不联网的应用做端到端加密的密钥交换协议，纯属浪费）；二是遗漏关键项（比如做了传输加密，却忘了本地锁屏)。以本仓库的应用为例，它是**完全离线**的：没有账号、没有服务端、数据只存在设备本地，用户主动导出/导入才会产生一个文件。这个定位直接简化了威胁模型——不需要考虑服务商信任、不需要考虑网络攻击面，核心风险收敛为"这台设备的物理/系统访问权限落到了不该拥有它的人手里"。

## 二、本地存储：默认加密，而不是"可选开启"

多数笔记应用的数据最终都落在本地数据库（SQLite/Room、Core Data、IndexedDB 等）里。默认情况下这些文件是明文的，任何拿到 root/越狱权限，或者从备份文件中提取数据的人都能直接读出全部内容。几个基本原则：

1. **静态加密（at-rest encryption）是目标，但两个平台达成它的成本差异很大**，做取舍时要老实承认这一点。iOS 借助系统级的 Data Protection 几乎是"免费"的——只要文件保护级别设对（`NSFileProtectionComplete`），不改一行数据库代码，未解锁状态下文件本身就不可读。Android 没有对等的免费选项：要给 Room/SQLite 加密，得引入 SQLCipher（原生库、schema 迁移、性能损耗）或自己在 `EncryptedFile` 之上重新搭一层存储，工程量和风险都不小。这也是为什么一些团队会先用"应用沙箱隔离 + 应用锁 + 关闭云备份"这类压缩风险面的组合作为第一阶段，把数据库级加密作为明确写进 backlog 的后续目标，而不是假装已经做到——**老实标注"我们现在做到了 A/B，C 还没做，原因是……"，好过在文档里含糊地把 C 也算作"已具备"**。

   本仓库的 Android 应用一度就停在那个第一阶段：Room 数据库是明文的，靠沙箱、可选的应用锁和关闭自动云备份压缩风险。现在这一项已经补上了——数据库通过 SQLCipher 打开，32 字节的随机密钥在首次运行时生成，存放在由 Android Keystore 托底的 `EncryptedSharedPreferences` 里，而不是应用自己的文件中。补做这件事时最容易被忽略的是**老版本留下的明文库**：SQLCipher 打不开它，如果不管，用户升级后会以为自己的记录全没了。可行的做法是在 Room 打开数据库之前先判断文件头（明文 SQLite 以 `SQLite format 3\0` 开头，加密库开头是随机盐），若是明文就用 `sqlcipher_export()` 导出到加密文件再替换回去，并记得把 `user_version` 一并带过去——`sqlcipher_export()` 会复制表结构和数据，但不会复制它，而 Room 正是靠这个值判断哪些迁移已经跑过。
2. **加密密钥不要和数据放在一起**。密钥应存放在系统提供的安全区域——Android 的 Keystore（可选绑定 StrongBox/TEE）、iOS 的 Keychain（结合 Secure Enclave）——而不是写死在代码里或存在明文配置文件中。
3. **关闭系统级自动云备份**，除非你能确保备份链路本身也是加密的、且密钥不会被一并备份走。Android 上这对应 `AndroidManifest.xml` 里的 `android:allowBackup="false"`；否则用户手机被 Google/iCloud 账号接管后，笔记可能连本体一起被同步走。
4. **导出文件同样要认真对待，但"默认写到哪"这件事，两个方向都有合理场景，不能一概而论**。很多应用做好了数据库加密，却在"导出为 JSON/CSV"这一步整体放弃了保护——悄悄把明文文件写进公共下载目录，用户自己都不一定知道多了一个文件、更别说别人能不能翻到它。避免这种"静默写入"有两条思路：一是写到应用私有目录，外部默认访问不到；二是用系统的存储访问框架（Android 上是 SAF，`ACTION_CREATE_DOCUMENT`）让用户在系统文件选择器里亲自选一个位置。两者要解决的其实是同一个问题——**不要在用户不知情的地方留下一份敏感明文**——私有目录是"藏起来"，SAF 是"让用户自己决定、自己心里有数"。哪种更合适取决于场景：应用私有目录更适合内部自动备份这类用户不需要直接接触的文件；而"导出"本身通常是用户主动发起、想要拿到手一份文件去转移或分享的操作，这时候替他悄悄选一个位置反而剥夺了他的知情权，用 SAF 让他自己选、自己承担"选哪儿"这个决定，是更尊重用户、也更符合 Android 分区存储（scoped storage）现状的做法。本仓库的应用采用的正是后者：导出走 `ActivityResultContracts.CreateDocument`、导入走 `OpenDocument`，位置完全由用户在系统选择器里决定。不管选哪条路，"导出前提示其中包含敏感信息""有条件的话支持给导出文件加密/加密码"这两点都值得做。

## 三、访问控制：本地锁 + 分级敏感度

"安全存储"解决的是数据在磁盘上的问题，"访问控制"解决的是数据在屏幕上的问题——也就是有人已经拿到了解锁的设备。

- **应用锁**：用系统的生物识别 API（Android `BiometricPrompt`、iOS `LocalAuthentication`）而不是自己实现指纹/密码比对逻辑，理由很简单——密码学正确性、防暴力破解、防降级攻击这些坑，系统 API 已经踩过了。从最近任务列表切换回来时要先出示锁屏、再渲染内容，避免内容"先闪一下"。

  至于"多久算超时"，"瞬间锁定"并不是无条件的最优解——它没考虑系统会短暂地把应用推到后台又立刻带回来的正常场景：调起系统分享面板、拉起相机/文件选择器、权限弹窗、旋转屏幕触发的 Activity 重建，都会短暂离开又返回。如果零容忍地"一离开就锁"，结果是用户分享一条记录后回来，还得再解锁一次——体验上等同于每次分享都被强制登出，长期只会让人关掉这个功能。更合理的做法是给一个刻意设得很短、只覆盖这类"系统接管又马上归还"场景的宽限期，而不是给一个宽泛的、覆盖"用户主动切走干别的事"的超时窗口——这是两回事：宽限期防的是误伤，超时窗口防的是"忘了手动锁"。本仓库的应用就是这么做的：切到后台后 10 秒内返回不会重新要求解锁，用来兼容"调起系统分享面板再返回"这一具体场景；超过 10 秒，或者是被切换到别的应用而不是系统分享面板，都会正常重新锁定。
- **防截屏/防录屏与最近任务缩略图脱敏**：Android 的 `FLAG_SECURE` 一行代码可以同时解决"最近任务列表里能看到明文缩略图"和"被截屏/录屏"两个问题，非常高性价比，几乎没有理由不加。iOS 没有对等的系统开关，通常做法是监听 `applicationDidEnterBackground`，切到后台前用一张遮罩视图覆盖内容。
- **敏感通知**：如果应用有推送/提醒功能（比如"该写日记了"），通知内容本身不要包含笔记正文片段，标题用中性文案。
- **分级锁定是进阶但值得考虑的设计**：不是所有内容都需要同一强度的保护。允许用户对"整个应用"设默认锁，同时允许给某几条特别敏感的记录设置"打开这一条需要再验证一次"，这样常用内容访问顺畅，真正敏感的内容有额外一道门。

本仓库的应用目前实现了前两条（可选的生物识别应用锁、隐藏最近任务缩略图/禁止截屏、关闭自动云备份），这是"轻量但覆盖了最常见泄露场景"的一个务实平衡点——没有为了"看起来更安全"去堆砌用户几乎不会用到的高级功能。

## 四、如果涉及同步/多端：端到端加密是唯一诚实的答案

一旦产品要做多设备同步或云备份，"安全私密"的复杂度会跳升一个量级。常见的三种做法，安全性依次递增：

1. **服务端明文存储**：最省事，但意味着服务商（以及任何入侵服务端的人）能读到全部内容。除非产品定位本就不承诺隐私，否则不建议。
2. **服务端静态加密（encryption at rest），密钥由服务端持有**：能防住"数据库被拖库"，但防不住服务商本身，也防不住服务商被合法要求交出数据/密钥。
3. **端到端加密（E2EE）**：加密和解密只发生在用户设备上，密钥从不以明文形式离开设备，服务端只存储密文，即使被攻破也无法读出内容。这是对"私密笔记"最诚实的承诺。

做 E2EE 时几个容易踩的坑：

- **密钥派生要用用户可控的秘密**（主密码、设备密钥对），并用成熟的密钥派生函数（Argon2id、PBKDF2 加足够迭代次数），不要自己发明算法。
- **"忘记密码就找回不了数据"是 E2EE 的必然代价，不是 bug**。如果产品同时宣传"E2EE"又提供"忘记密码一键找回全部笔记"，这两者是矛盾的——要么密钥托管在服务端（不是真正的 E2EE），要么找回的只是账号而不是历史数据。把这个权衡诚实地告诉用户，比暗中留一个后门更负责任。
- **多设备场景下的密钥同步**本身也要加密传输（比如用户在新设备上输入主密码，通过安全通道从旧设备或服务端取回被加密保护的主密钥），避免"每台新设备都重新生成密钥导致历史数据读不出来"这种体验灾难。

## 五、界面设计也是安全设计的一部分

安全不只是后端和存储层的事，界面呈现方式同样会造成信息泄露：

- **视觉上是否要"淡化"内容的敏感性，是一个需要权衡、而不是照抄的决定**。一种思路是：鲜艳的强调色、封面缩略图预览文字，都会让人在别人瞥一眼屏幕时立刻意识到"这是一个私密记录类应用"，所以选择偏中性、偏"工具感"的视觉语言，降低"被路过的人一眼认出这是什么"的概率。这个理由是成立的，但它要付出的代价同样真实：一个刻意去掉所有温度的界面，会让"坐下来写点什么"这件事变得更难开口，而对一个 CBT 练习工具来说，用户愿不愿意打开它、愿不愿意写完，本身就是产品成败的关键。

  本仓库的应用最后选了相反的方向——通篇做成纸质笔记本的样子（米黄纸张、衬线字体、一条页边线），因为它要鼓励的恰恰是"像写日记一样坐下来写"。这是一个明确的取舍：它放弃了一部分"别人瞥一眼认不出这是什么"的伪装性，换取更低的书写心理门槛。之所以敢这么换，是因为防"被别人看到"这件事并没有依赖视觉伪装来承担——应用锁、`FLAG_SECURE`（最近任务缩略图脱敏 + 禁止截屏）、列表不显示正文预览，这些才是真正扛住威胁模型的部分。**视觉伪装是最弱的一层防护，不该让它去背本该由技术手段承担的责任**；反过来说，当技术层面的防护到位时，把视觉风格的选择权交还给产品目标，是合理的。
- **锁屏文案不剧透**。锁屏提示语应该只说"解锁查看内容"，不要写出应用具体记录的是什么主题。
- **应用图标与应用名**在锁屏和桌面上也是可被他人看到的信息面，如果场景要求更高的伪装性，可以考虑允许用户自定义显示名称/图标（这属于更进阶的"伪装"需求，需要单独评估是否是产品要支持的场景）。
- **深色/浅色两套主题要经过同样的推敲**，而不是只优化一套、另一套简单反色了事——同一套配色逻辑（包括"哪些信息默认不显示"这类决定）在两种模式下都要成立。

## 六、可核查性：把"我们说的"变成"用户能验证的"

最后一层，也是最容易被忽视的一层：安全声明需要是可核查的，而不是营销话术。

- **开源，或至少公开关键的安全实现细节**（用了哪种加密算法、密钥怎么存、有没有做静态加密），让愿意验证的用户或第三方能够核实。
- **完全离线的应用，"不联网"本身就是最强的隐私承诺之一**——建议显式声明"没有账号、没有服务端、除非你主动导出，否则数据不会离开这台设备"，并且工程实现上真的做到零网络请求（比如构建时不引入任何网络库、CI 里可以加一个静态检查确认没有意外的网络调用被引入）。
- **权限最小化**。App 请求的系统权限（相机、麦克风、位置、通讯录……）应该严格对应功能需要，一个笔记应用如果申请了位置权限却没有任何用到定位的功能，会直接削弱"我们重视隐私"这句话的可信度。
- **对外部依赖保持警惕**：第三方 SDK（崩溃上报、统计分析、广告）往往是数据泄露最隐蔽的来源，即使应用自身逻辑无懈可击，一个会上传用户行为数据的 SDK 也会让全部努力归零。私密类应用应该优先做到零第三方数据收集 SDK，或者至少清楚罗列每一个 SDK 收集了什么、发到哪里。

## 小结

安全私密的笔记应用不是靠某一个"加密"功能实现的，而是一整条链路上多层防护叠加、且每一层都要根据平台成本和真实使用场景做取舍的结果：明确威胁模型 → 本地静态加密（以及补做它时别忘了老版本留下的明文库怎么迁移） → 应用锁用短而精确的宽限期区分"系统临时接管"和"真的离开了" → 导出这类用户主动发起的操作优先让用户自己选目的地，而不是替他默默决定 → 如果涉及同步则做真正的端到端加密而非营销话术 → 让技术手段而不是视觉伪装去扛威胁模型，从而把视觉风格的选择权留给产品目标 → 用可核查的方式兑现每一句安全承诺，包括承认还没做到的部分。这些取舍没有放之四海而皆准的答案——同一条"最佳实践"在 iOS 和 Android 上的落地成本可能天差地别，"更安全"的方向有时候恰恰是把选择权交还给用户而不是替他做主。把复杂度和诚实的自我披露都花在真正对应威胁模型的地方，而不是堆砌一份读起来漂亮、却和自己的应用对不上号的"看起来安全"的功能列表，才是这类产品设计中最重要的判断力。
